# Четвёртый этап: конвейер стандартного отчёта

База этапа: `01a29bec` (`main`, после выпуска 1.3.0).

## Архитектура

Стандартная аппаратно-системная диагностика внутри single-file `arm_info.sh`
выполняется явным конвейером:

1. `collect_base_snapshot` собирает и нормализует факты ОС, CPU, памяти,
   сети, файловых систем, журналов, служб, RAID/ECC, батареи и SMART;
2. `evaluate_base_disk_scores`, `evaluate_base_disk_findings`,
   `evaluate_base_network_status` и `evaluate_base_snapshot` преобразуют
   нормализованные факты в score/status/confidence и рекомендации;
3. `prepare_base_output_view` применяет privacy к представлению снимка;
4. выбирается ровно один renderer: `emit_base_text` или `emit_base_json`.

Collector не формирует рекомендации и не выполняет scoring/status
classification. Для воспроизводимого disk scoring в `DISK_CHECK_ROWS`
сохраняются роль диска, SMART-факты, ресурс, температура и NVMe
Available Spare/Threshold.

Наличие `smartctl` и UID определяется один раз, поэтому emitters не повторяют
hardware/system probes. Корпоративные collectors и нормализованный снимок
CIFS/autofs/GVFS/GIO этапа 3 не менялись.

## Совместимость

- версия остаётся 1.3.0 до отдельного решения о следующем релизе;
- standard JSON сохраняет schema v1 и прежний набор групп/полей;
- TXT-разделы, тексты рекомендаций, scoring и exit codes сохранены;
- действующие пороги disk/network scoring перенесены без изменения значений;
- `--privacy`, `--save`, quiet-режим и выбор каталога отчёта работают как раньше;
- поставка остаётся однофайловой и read-only по умолчанию.

## Регрессии

`tests/test_stage4_base_pipeline.sh` проверяет:

- наличие и порядок стадий конвейера;
- отсутствие рекомендаций, scoring и status classification в collector;
- отсутствие повторных hardware/system probes в renderers;
- воспроизведение disk scoring из нормализованных SMART-фактов;
- сохранение сетевой классификации;
- прежний порядок HDD/NVMe-рекомендаций.

Прежние `test_cli.sh` и `test_sections.sh` продолжают проверять реальный TXT,
JSON schema v1, privacy, рекомендации и пользовательские разделы.

## Контрольный замер

Среда разработки, 18 сентября 2026 года; три последовательных запуска
`bash arm_info.sh --json --privacy`, медиана:

| Вариант | Медиана |
|---|---:|
| До этапа 4 (`01a29bec`) | 1,112 с |
| После этапа 4 | 1,001 с |

Нормализованный JSON до и после исходного Stage 4 refactor совпал после
исключения времени генерации, текущего load average и сетевых счётчиков,
которые меняются между последовательными запусками. Верхнеуровневые ключи,
ключи всех групп, schema v1 и exit code совпали.

Замер не доказывает ускорение на любом АРМ и не заменяет полевой прогон на
РЕД ОС 7/8, но регрессии быстродействия в контрольной среде не показал.
