# Корпоративные профили

Начиная с версии 1.2.0 `arm_info` поддерживает отдельные read-only профили для корпоративных рабочих станций РЕД ОС. Они не входят в аппаратный health score и предназначены для оперативной диагностики инфраструктурных проблем.

> **С версии 1.2.1 все профили встроены в `arm_info.sh`. На проверяемый АРМ достаточно перенести один файл; `arm_info-enterprise.sh` больше не требуется.**

Короткий запуск полного корпоративного профиля: `sudo arm_info -c`. Ключ `-c` является алиасом `--corp`; оба варианта эквивалентны `--profile enterprise` и включает только `domain + network + print`. Инвентаризация ПО выполняется только по явному `--profile software`.

Начиная с **1.2.2**, TXT-отчёт корпоративных профилей выводится в выровненных колонках; длинные значения и обычный текст рекомендаций переносятся по ширине терминала. Для каждой команды в рекомендациях в скобках выводится краткое объяснение результата команды. При интерактивном TXT-запуске корпоративного профиля экран предварительно очищается; JSON не загрязняется управляющими последовательностями.

В **1.2.3** команды в рекомендациях печатаются одной физической строкой без принудительного `fold`. Терминал может визуально перенести длинную команду, но при копировании pipeline, regex и аргументы остаются цельными. Пояснение к команде выводится отдельной строкой в скобках.

В **1.2.4** команды рекомендаций прошли отдельную ревизию: исправлены формы `nmcli` для DNS/802.1X, Kerberos-проверки учитывают контекст рабочего пользователя, сетевые проверки DC получили timeout, CUPS/RPM/RAID-команды уточнены. Служебные значения задаются именованными токенами (`DOMAIN_FQDN`, `DC_FQDN`, `USER_NAME`, `PROFILE_NAME`, `CERT_PATH`, `QUEUE_NAME` и др.), которые нужно заменить фактическими значениями. Команды, меняющие состояние, явно помечаются `ИЗМЕНЯЕТ СОСТОЯНИЕ`.

`-c` / `--corp` и остальные профили **по умолчанию ничего не сохраняют**: результат выводится только в терминал. Файл создаётся только при явном `-s` / `--save`. Без `-o` имя формируется автоматически в текущем доступном для записи каталоге (при необходимости используется `/tmp`); для `--corp` сохраняется префикс `ARM_INFO_CORP_`. Через `-o FILE` можно задать точный путь, а через `-o DIR` — каталог; `-o/--output` без `-s/--save` считается ошибкой CLI.

## Профили

### `domain`

Проверяет:

- определение домена через `realm`, `sssctl`, `sssd.conf` или FQDN;
- состояние `sssd`;
- `adcli testjoin` при наличии `adcli`;
- наличие действующего Kerberos ticket и число доступных credential cache;
- синхронизацию времени (`timedatectl`, дополнительно `chronyc`);
- количество записей с признаками ошибок Kerberos в журнале SSSD за текущую загрузку;
- DNS suffix/search;
- разрешение FQDN;
- `_ldap._tcp`, `_kerberos._tcp` и `_ldap._tcp.dc._msdcs` SRV;
- доступность найденных контроллеров по TCP 88/389; список не ограничивается тремя узлами, дубли имён удаляются; каждый найденный DC выводится отдельной строкой `Контроллер #N` со статусом Kerberos 88 и LDAP 389, после чего сохраняется общий итог TCP-проверок.

```bash
sudo arm_info --profile domain
sudo arm_info --profile domain --privacy --json --save -o /tmp/domain.json
```

Список DC отражает обнаруженные DNS SRV узлы, а не число активных соединений клиента. Он зависит от ответов используемого DNS и выбранного домена.

TCP-проверки выполняются ограниченной очередью и используют общий бюджет активной сетевой диагностики вместе с CIFS/GIO. По умолчанию одновременно выполняются четыре TCP-проверки, а бюджет составляет 30 секунд. Исчерпание бюджета не удаляет DC из отчёта: непроверенные порты получают N/A. Для больших инфраструктур лимиты можно задать явно: `sudo arm_info -c --network-budget 60 --network-jobs 6`.

В `--corp` DNS собирается один раз в `DNS / DOMAIN`; отдельный профиль `network` сохраняет свой раздел `DNS`.

### `network`

Проверяет:

- default gateway и активные IPv4-интерфейсы;
- источник DNS-конфигурации и upstream DNS;
- ситуацию с `127.0.0.53`, когда upstream DNS не определяется;
- FQDN и доменные SRV;
- **все настроенные** NetworkManager-профили, содержащие признаки 802.1X, и отдельно число активных;
- EAP-метод и параметры основного/phase2 профиля;
- пути/источники клиентского и CA-сертификатов;
- PEM/DER X.509: Subject, Issuer, дату начала, дату окончания и остаток срока;
- `file://`, PKCS#11/blob, `system-ca-certs`, `ca-path`, private-key/PKCS#12;
- безопасный fallback-поиск host-named сертификата в `/etc/pki/tls` и `/etc/pki/tls/certs`, если NetworkManager не возвращает certificate reference;
- CIFS mounts и зависшие/недоступные точки монтирования;
- GVFS mounts, `caja`, `gvfsd-smb` и `gvfsd-fuse`.

Проверка CIFS/GVFS использует короткий timeout и общий бюджет активной сетевой диагностики, чтобы сама диагностика не зависла на недоступном ресурсе. После исчерпания бюджета уже обнаруженные ресурсы остаются в отчёте как непроверенные. Для CIFS проверяется не только наличие mount: `arm_info` получает TARGET одной колонкой и выполняет полный readdir каталога плюс metadata lookup одного элемента. GVFS-подключения теперь проверяются тем же фактическим чтением в контексте владельца `/run/user/<UID>/gvfs`, а не через metadata-only `stat -f`. Перечисление имён GVFS также выполняется под владельцем и с таймаутом, без фильтра по доступности каталога. Каждый ресурс показывается отдельной строкой, SMB-нумерация продолжается после CIFS. Недоступный список отмечается как неполная диагностика, а не «нет подключений». Успешная проверка подтверждает перечисление каталога и чтение метаданных в момент запуска; она не гарантирует открытие каждого файла, права записи или отсутствие клиентского кэша. Проверяются локальные CIFS, GVFS/FUSE и SMB mounts пользовательского GIO через `gio mount -l`. Для GIO используется D-Bus адрес desktop-процесса (либо runtime bus), а доступность проверяется `gio list` под владельцем; совпадающие GIO/FUSE ресурсы в одной сессии не дублируются. Закладки без подключения не считаются mounts. Если сессия недоступна, выводится неполная диагностика; TARGET с пробелами и кириллицей сохраняются без разбиения/hex-экранирования.

### `print`

Проверяет:

- состояние `cups.service` и CUPS scheduler;
- принтер по умолчанию;
- число очередей;
- paused/disabled/stopped queues;
- число текущих заданий;
- backend URI без раскрытия логина/пароля;
- warnings/errors CUPS за текущую загрузку.

```bash
sudo arm_info --profile print
```

### `software`

Выполняет глобальную инвентаризацию всех установленных RPM-пакетов без списка заранее заданных приложений. Для каждого пакета фиксируются имя/архитектура и версия-релиз. Дополнительно выводятся общее число процессов и количество zombie-процессов.

Профиль предназначен для отдельного запуска, когда нужна инвентаризация или сравнение двух АРМ. В общий корпоративный отчёт он не включён, чтобы не раздувать оперативную диагностику сотнями строк.

### `enterprise`

Внутренний CLI-ключ `enterprise` сохранён для совместимости. Пользовательский TXT-отчёт при `-c`/`--corp`/`--profile enterprise` имеет шапку `ARM_INFO КОРПОРАТИВНЫЙ` и `Профиль: корпоративный`.

Последовательно запускает `domain + network + print`. Глобальная инвентаризация ПО выполняется отдельно через `--profile software`.

Рекомендуемый запуск:

```bash
sudo arm_info -c
sudo arm_info --corp --privacy --json --save -o /tmp/arm-corp.json
```

Первый вариант выводит корпоративный TXT-отчёт только в терминал. Чтобы сохранить его, используйте `sudo arm_info -c --save` или `sudo arm_info --corp --save`; для фиксированного имени/расположения добавьте `-o PATH`. JSON работает по тому же правилу: без `--save` файл не создаётся.

Полная форма `--profile enterprise` сохранена для совместимости.

## Рекомендации

Для каждого `WARN`, `CRIT` и `N/A` профиль формирует расширенную рекомендацию. Она содержит: исходную проверку и значение, возможные причины, влияние на АРМ, что проверить, безопасный порядок действий, набор диагностических/восстановительных команд и критерий контроля результата.

Начиная с 1.2.4 каждая команда получает отдельное описание ожидаемого результата. Shell pipeline сохраняется одной командой; несколько независимых команд отображаются отдельно. Вместо placeholders вида `<DOMAIN>` используются безопасные токены без shell-метасимволов: `DOMAIN_FQDN`, `DC_FQDN`, `DC_IP`, `USER_NAME`, `PROFILE_NAME`, `CERT_PATH`, `MOUNT_PATH`, `QUEUE_NAME`, `JOB_ID`, `PARENT_PID` и др. Перед выполнением такой команды токен нужно заменить фактическим значением. Команды, меняющие состояние (`cupsenable`, `cupsaccept`, `cancel`, установка пакета), получают явную пометку `ИЗМЕНЯЕТ СОСТОЯНИЕ` и не выполняются автоматически.

Полный контракт и ограничения команд описаны в [COMMANDS.md](COMMANDS.md).

Рекомендации также присутствуют в JSON как массив `recommendations[]`, поэтому их можно использовать в helpdesk/автоматизации без разбора текстового отчёта.

## Privacy

Для отчётов, которые покидают внутренний контур, используйте `--privacy`. Профили скрывают доменное имя, hostname, MAC, адреса DNS и маскируют IP; printer URI всегда очищается от встроенных учётных данных. Автоматическое имя корпоративного privacy-отчёта также не содержит hostname.

## Exit codes

- `0` — проблем не обнаружено;
- `1` — есть предупреждения;
- `2` — есть критическое отклонение;
- `3` — часть проверки недоступна из-за отсутствующих утилит/данных, при этом критичных проблем нет;
- `64` — ошибка CLI.

## Сравнение двух АРМ

Снимите JSON на двух рабочих станциях:

```bash
sudo arm_info --corp --privacy --json --save -o arm-a.json
sudo arm_info --corp --privacy --json --save -o arm-b.json
```

Затем:

```bash
arm_info --compare arm-a.json arm-b.json
```

Или машинно-читаемо:

```bash
arm_info --compare arm-a.json arm-b.json --json
```

Сравнение умеет работать и с обычными JSON-отчётами `arm_info`: для schema v2 сравниваются стабильные ключи `checks`, для остальных JSON выполняется рекурсивное сравнение с исключением очевидно изменчивых полей времени/отчёта.

Код `0` означает отсутствие отличий, код `1` — отличия найдены.

## Зависимости

Профили используют только уже установленные компоненты и не меняют конфигурацию. Максимальная полнота достигается при наличии `sssd-tools`, `adcli`, `krb5-workstation`, `bind-utils` (`dig`/`host`), `NetworkManager`, `openssl`, `cups-client`, `nc`/`nmap-ncat` и `python3` для `--compare`.

Отсутствующая утилита не делает базовый `arm_info` неработоспособным: соответствующая проверка получает состояние `N/A`/`unknown`.

## Отображение 802.1X сертификатов

`network` и `enterprise` проверяют все настроенные NetworkManager-профили на признаки 802.1X, включая `802-1x.client-cert`, `802-1x.ca-cert`, `802-1x.phase2-client-cert`, `802-1x.phase2-ca-cert` и private-key поля. Для PEM/DER-файлов выводятся Subject/Issuer, дата начала, дата окончания и остаток срока. Значения `file://` читаются через `nmcli -e no`; PKCS#11/blob фиксируются как источник без попытки интерактивного запроса PIN.

Если NetworkManager не возвращает ссылку на сертификат, host-named X.509 может отображаться как `Сертификат АРМ (кандидат 802.1X)`. Такая строка означает найденный на хосте подходящий сертификат, но не утверждает связь с конкретным NM-профилем без подтверждающего reference.

### CUPS: журнал и очистка заданий

Счётчик warning/error учитывает JSON-записи journalctl приоритетов 0–4 за текущую загрузку, без заголовков и `No entries`. Ноль записей — OK, хотя бы одна — WARN с рекомендациями, недоступный журнал — N/A. Старое сообщение не доказывает текущий сбой. Отсутствующий принтер по умолчанию — INFO.

В рекомендациях печати `cancel -a` отменяет все задания во всех очередях выбранного CUPS-сервера (для чужих заданий нужны права); `cancel -a QUEUE_NAME` ограничивает отмену одной очередью. Команда помечена как изменяющая состояние, автоматически не выполняется, не очищает Windows print-server и не устраняет первичную причину ошибки. См. [CUPS cancel(1)](https://openprinting.github.io/cups/doc/man-cancel.html).
